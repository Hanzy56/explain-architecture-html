# 業務とアーキテクチャをHTMLで説明する

対象プロジェクトの業務を入口に、読み進める説明ページと、ノードを選んで探索する詳細図を作る。既定は **説明 `index.html` ＋詳細図 `architecture.html`** の2ページ。ユーザーが別の形式・ツール・配置を選んでいる場合はその選択に合わせる。

## 調査と構成

1. 対象のルート、プロジェクト指示、参照revision、変更状態を確認する。requirementsは業務判断、code/schema/testsは実装の根拠として読み、実際の入口から状態変更・永続化・外部作用までつながる範囲を追う。宣言された構成と現在稼働中の構成は区別する。
2. 業務の開始・担当者・分岐・成立条件・完了を整理する。並行する状態を一本の順番へ押し込めず、例外は主な流れの近くで説明する。ライブラリやCLIなら、その利用者の作業の流れを業務に相当する入口として使う。
3. 先に業務フロー、次に全体構成、その後に業務の各段階を支える仕組みを説明する。段階と技術説明をリンクで結ぶ。簡略図の責務説明はその図に登場する要素に合わせ、外部サービスなどの細かな責務は詳細図へ置く。セクション数は内容に合わせる。

具体的な原稿・図・根拠の組み立てでは [authoring.md](references/authoring.md) を読む。図と説明の主張が根拠に対応し、未解決の点が読者の誤解を招かない形で示されれば調査を終える。

## 生成と見せ方

既定では、説明文と小さな処理図にAnswer me with HTML、詳細な構成図にArchifyを使う。両方のツールのインストールを前提にしない。初回の準備・再生成では [rendering.md](references/rendering.md) を読み、同梱のスクリプトを使用する。対応する版を作業専用の一時ディレクトリへ取得し、グローバル設定や対象アプリの依存関係を変更せずに生成する。

- 説明ページは、依頼の言語で書く。冒頭は余計な右余白を設けず、文の区切りを段落で表す。
- 詳細図への導線を、参照リンクより目立つ案内カードにする。別ページの詳細図に「説明ページへ戻る」を付け、対応する本文の位置へ戻す。
- 詳細図では、業務での役割と接続先を先に見せ、根拠コードは後ろで展開する。直接接続と、複数段先までの上流・下流の違いを、その場で説明する。
- 日本語では日本語フォントを優先する。説明と詳細図のGitHubなどの外部参照は新しいタブで開く。
- 説明と詳細図は共通ヘッダーで切り替える。「表示設定」で明暗（自動・ライト・ダーク）とデザイン（標準・図面）を共有し、「コピー・出力」はページに合った操作を見せる。詳細図の「図に集中」では補足や役割一覧を隠し、図の領域と常設の戻る操作を確保する。
- 読者向けのページには、内容の理解に必要な情報と根拠を載せる。制作ツールの比較・制作履歴は、求められた場合に別の報告へ置く。参照revision・ツールの版・検証hashは同梱の検証記録に残し、ライセンスは保持する。

表示調整は作業用rendererまたは再実行できる後処理へまとめる。ArchifyのHTMLは生成後に直接書き換えず、rendererを調整してから検証付きで生成する。既存ページの修正では原稿・図の仕様・表示調整を更新し、同じ成果物へ反映する。

## 確認と納品

HTMLの生成・構造の検査に加え、ブラウザで本文と図を実際に確認する。最低限、狭い画面とデスクトップ、操作部品と見出しの重なり、主なリンクの往復、外部リンクの新規タブ、テーマ切替を確認する。フォントへの指摘がある場合は実際の描画フォントも確認する。詳しい検査方法と補助スクリプトは [rendering.md](references/rendering.md#表示確認) にある。

完了時は、対象ソースのidentity、最終HTMLのhash、実行した検証とその結果を記録し、ユーザーが開ける絶対パスで説明ページを渡す。配布する場合は同じフォルダに両HTML・編集用原稿と仕様・必要なライセンスを含め、明示したファイルだけをまとめる。未実施のブラウザ確認や本番確認を成功として扱わない。
